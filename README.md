# transport-sharing — сервис шеринга самокатов

Учебный/тестовый проект: клиент-серверный сервис шеринга электросамокатов.
Пользователь находит свободный самокат на карте, бронирует его, едет и платит по факту.

**Стек:** React 19 + Vite 8 + TypeScript + Tailwind 4 + OpenLayers (фронт) ·
Node.js 22 + Fastify 5 + pg + ws (бэкенд) · PostgreSQL 17 · Docker Compose (3 контейнера).

## Требования к машине

- **Docker Engine 24+ с Compose v2** — и больше ничего. Проверка: `docker compose version`.
- Свободные порты `8088` (интерфейс) и `5433` (база; нужен только для отладки). Если заняты —
  см. «Порты и переменные».
- Около 2 ГБ свободного места под образы.

**Node, npm, Python и PostgreSQL на хосте не нужны.** Всё, что требуется сервису, ставится внутри
образов: сборка фронта и запуск бэкенда идут на `node:22-alpine` (там же `npm ci` по lock-файлу),
статика раздаётся `nginx:1.27-alpine`, база — `postgres:17-alpine`. Поэтому запуск на «сырой»
машине — это один `docker compose up`; локальный Node нужен только для dev-режима и e2e-прогонов
(см. [`docs/RUNBOOK.md`](docs/RUNBOOK.md)).

## Быстрый старт

```bash
git clone https://github.com/Verticool/transport-share.git
cd transport-share
docker compose up -d --build
```

Три команды по очереди: склонировать, перейти в каталог, собрать и запустить три контейнера
(база, бэкенд, фронт). Строки разделены намеренно — так набор команд одинаково работает в любом
терминале (bash, PowerShell, cmd) и его можно просто выполнить построчно.

Интерфейс — <http://localhost:8088>. Схема и данные применяются автоматически: одноразовые сервисы
`db-migrate` (миграции) и `db-seed` (наполнение из `mock/`) выполняются до старта бэкенда — порядок
задан через `depends_on`, так что при первом запуске база создаётся с нуля и сразу наполнена.

Остановить: `docker compose down` (данные базы сохраняются). Полный сброс — `docker compose down -v`:
том удаляется, и следующий `up` снова создаёт и наполняет базу с холодного старта.

## Порты и переменные

Все настройки лежат в [`.env`](.env) в корне репозитория. Значения по умолчанию те же, что в
compose, поэтому запуск работает и без правок; править `.env` нужно только под свою машину
(типичный случай — занятый порт).

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `FRONTEND_PORT` | `8088` | порт интерфейса на хосте |
| `DB_PORT` | `5433` | порт базы на хосте (для `psql` при отладке; внутри сети база всегда на 5432) |
| `DB_NAME`, `DB_USER`, `DB_PASSWORD` | `sharing` | база и её креды; из них собирается строка подключения для миграций, сида и бэкенда |
| `LOG_LEVEL` | `info` | подробность логов бэкенда (`fatal`…`trace`) |
| `ACCESS_TOKEN_SECRET` | дев-значение | подпись токенов доступа |
| `ACCESS_TOKEN_TTL_MINUTES` | `120` | срок жизни токена доступа |
| `REFRESH_TOKEN_TTL_DAYS` | `30` | срок жизни токена обновления |
| `SIM_TICK_MS` | `1000` | шаг симулятора парка (движение и расход заряда) |
| `BOOKING_TICK_MS` | `5000` | шаг обслуживания броней (снятие просроченных, предупреждение) |
| `VITE_API_MODE` | `http` | источник данных в собранном фронте: `http` — с сервера, `mock` — из `mock/*.json` без базы |

Занят порт (или нужен другой) — поменяйте `FRONTEND_PORT` в `.env` и выполните

```bash
docker compose up -d
```

Разово, без правки файла — переменная перед командой; синтаксис зависит от терминала:

```bash
FRONTEND_PORT=8090 docker compose up -d
```
```powershell
$env:FRONTEND_PORT = 8090
docker compose up -d
```

Порт меняется только для доступа снаружи: внутри compose-сети сервисы общаются по своим
стандартным портам, и фронт проксирует `/api` и `/ws` к бэкенду, так что адреса в коде не
зависят от выбранных портов.

Тарифов и порогов парка в `.env` нет намеренно: это доменные значения (`shared/src/`), одинаковые
для мок-режима, бэкенда и тестов. Вынести их в окружение — значит разрешить запуск с тарифами,
которые не совпадают с проверенными в приёмке.

### Почему `.env` лежит в репозитории

Намеренно. Секретов в проекте нет: база поднимается локально тем же `docker compose`, креды
демонстрационные, токены подписываются дев-значением, внешние сервисы (почта) эмулируются. Смысл
файла в репозитории — чтобы проект запускался сразу, без шага «скопируйте пример и поправьте»:
`docker compose up -d --build` — всё. Если значения понадобится изменить, правится один файл,
и это видно в истории: смена порта или шага симулятора — обычный коммит.

## Что появляется в базе после сида

Сид идемпотентный и наполняет базу из `mock/*.json` — проверено на холодном старте
(`docker compose down -v`, затем `up -d --build`): **40 самокатов** во всех четырёх состояниях —
`free` 19, `reserved` 6, `in_ride` 5, `unavailable` 10 (недоступные в том числе разряженные ниже
порога: такие не показываются свободными — требование ТЗ), **7 пользователей** (у `demo@` 8 поездок
и 8 счетов, у остальных от 2 до 8) с историей поездок, счетов и писем. Тарифы в базе не хранятся:
это константы домена в `shared/src/`, одинаковые для сервера, мок-режима и тестов. Один самокат (`SC-030`) стоит вне зоны обслуживания
с открытой поездкой — на нём проверяется блокировка мотора с возвратом в зону.

Проверить состояние парка после запуска:

```bash
docker exec sharing-db psql -U sharing -d sharing -t \
  -c "select status, count(*) from scooters group by status order by 1;"
```

## Как убедиться, что работает

- `bash scripts/demo.sh` — поднимает стек и прогоняет сценарии снаружи, через тот же адрес, что
  видит браузер: состояние парка, поток событий, две брони одновременно (вторая получает отказ).
- `npm run check` — типы, lint и юнит-тесты всех пакетов (нужен локальный Node 22).
- Playwright против контейнеров: живой набор в `frontend/e2e-live/` (два клиента, бронь, поездка,
  выезд из зоны). Запуск описан в [`docs/RUNBOOK.md`](docs/RUNBOOK.md) §4.

Пункт-в-пункт соответствие ТЗ и сырые выводы проверок — [`docs/ACCEPTANCE.md`](docs/ACCEPTANCE.md).

## Два режима источника данных

`VITE_API_MODE=http` (по умолчанию в контейнере) — данные с сервера, общие для всех клиентов:
одно состояние на всех через REST и WebSocket. `mock` — данные из `mock/*.json` и «сервер» в
памяти вкладки: интерфейс можно смотреть без базы вовсе. Dev-режим без Docker — в
[`docs/RUNBOOK.md`](docs/RUNBOOK.md).

## Структура

```
shared/    доменный контракт: типы, zod-схемы, тарифы, деньги, время, зона, ws-протокол, симулятор
frontend/  React SPA: карта парка, бронь, поездка, кабинет, счета, эмуляция почты
           два источника данных за одним интерфейсом (моки и сервер), сборка в nginx-образ
backend/   Fastify: REST + WebSocket-хаб, симулятор парка, миграции SQL, сид из mock/
mock/      сид-данные JSON — источник для БД и для режима моков в интерфейсе
prompts/   задания, отданные AI-воркеру (требование сдачи промптов)
scripts/   служебные скрипты: demo.sh (сценарий приёмки), сброс демо-данных, проверки
docs/      план, архитектура, рулсет, ADR, приёмка, evidence
```

------------------------------------------------------------------------------
2) Почему диспетчер задач занижает llama-server

Диспетчер показывает колонку «Память», то есть active private working set. Модель
KAT-Coder-V2.5-Dev-APEX-Compact.gguf (16,5 ГБ) загружена через mmap: это file-backed
страницы, которые система вправе выгрузить, и в колонку «Память» они не попадают.
Реальную величину показывает private bytes (commit): 28,57 ГБ, из них ~16,5 ГБ — сама
модель, остальное — host-буферы CUDA, workspace cuBLAS и KV/буферы слотов.

Вывод: ориентироваться надо на commit (лимит 47,2 ГБ), а не на цифру из диспетчера.

------------------------------------------------------------------------------
3) Риск и что с ним делать

Риск на момент замера: commit 90,3% — свободно ~4,6 ГБ. Фатального отказа нет, но
параллельный запуск Docker Desktop (vmmem/WSL2 легко берёт 2-8 ГБ) или тяжёлого
браузера приведёт к отказу аллокаций или свопу и «залипанию» машины.

Меры (по возрастанию вмешательства):
  1. Не держать одновременно: воркеры + Docker Desktop + тяжёлый браузер.
  2. Держать не более 1-2 воркеров (уже зафиксировано: max_concurrent_children=2).
  3. Уменьшить аппетит llama-server при следующем перезапуске: `-c 131072` и/или `-np 2`
     (KV и host-буферы слотов пойдут вниз; замер до/после обязателен, цифры заранее не обещаем).
  4. Увеличить pagefile — поднимает commit limit (ценой скорости при свопе).

Контроль: `E:\llama.cpp\ram-guard.ps1` (вне репозитория — утилита машины, не часть проекта) —
печатает physical/commit/llama-server и возвращает 0/1/2 (норма / предупреждение / критично).
Проверять перед делегированием воркерам и перед `docker compose up`.

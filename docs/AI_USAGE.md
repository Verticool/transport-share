# AI_USAGE.md — как проект делается с AI-агентами (требование ТЗ №6, №7)

Скрывать нечего: проект собирается парой «сильный оркестратор + локальный воркер».
Ниже — кто что делает, чем это проверяется и где лежат сырые промпты.

## 1. Роли

| Роль | Кто | Что делает |
|---|---|---|
| Оркестратор | Hermes Agent (модель уровня frontier, API) | планирование стадий, фиксация контракта, раздача микрозадач, **приёмка замером**, сборка docker, e2e, документация |
| Воркер | KAT-Coder-V2.5-Dev-APEX-Compact (GGUF, 16.5 ГБ) на `llama.cpp`, RTX 3090, локально | генерация компонентов, мок-данных, сервисов по готовому контракту |
| Пользователь | Евгений Гудошников | приоритеты, согласование решений, финальная приёмка |

Модель воркера указана явно: `E:\models\KAT-Coder-V2.5-Dev-APEX-Compact.gguf`,
сервер `llama-server` на `127.0.0.1:8080`, alias `kat-coder`.

## 2. Протокол делегирования

1. Оркестратор фиксирует контракт (`shared/`) и пишет микрозадачу на 1–2 файла (до ~200 строк каждый).
2. Задача содержит **два списка**: что сделать и **что НЕ трогать**; каждое требование — с числовым
   критерием, который оркестратор сможет замерить (перекрытие 0 px, grep пуст, 40 элементов в DOM).
3. **Воркер только пишет код.** Ему запрещено крутить линтер и тесты циклами: один финальный прогон
   для отчёта — и всё. Приёмка, разбор ошибок и список того, что править, — работа оркестратора.
   Причина измерена: один воркер за 15 минут сделал 119 tool-call'ов, где большинство — повторные
   `eslint | vitest` после каждой микроправки, и всё это время занимали запросы к модели, а не работа.
4. **Один воркер одновременно.** Два параллельных сабагента на одной GPU дают ту же суммарную
   пропускную способность (~122 t/s), но каждая задача идёт вдвое медленнее (60 t/s против 100+),
   и обе быстрее упираются в лимит контекста. Параллелить стоит только независимые мелочи.
5. Воркер работает строго внутри заданной папки; браузерных проверок ему не даётся (у него нет браузера) —
   только grep, тесты, HTTP.
6. Оркестратор принимает работу заново: `tsc --noEmit`, `vitest`, `eslint`, grep, замер в браузере.
   Отчёт воркера = самоотчёт, не факт. Мелкие дефекты (ошибка типа, неверный путь в декларации,
   подгонка теста) оркестратор исправляет сам — обычно это быстрее, чем ещё один цикл воркера.
7. Сырые промпты сохраняются в `prompts/S<стадия>-<номер>-<тема>.md`; батч-итог — в `docs/evidence/`.

## 3. Границы автономии воркера

- Не трогает `docs/`, `shared/`, `docker-compose.yml`, миграции — только назначенные файлы.
- Не запускает dev-серверы на занятых портах, не устанавливает пакеты без явного разрешения.
- Не принимает архитектурных решений: при неоднозначности останавливается и возвращает вопрос.
- Не является источником истины: любое «готово» проверяется оркестратором независимо.

## 3.1 Типизация и валидация в заданиях воркеру (RULES §F)

Каждое задание обязано содержать эти ограничения дословно, иначе воркер закроет несоответствие типов кастом:

- **Запрещены приведения типов**: `as any`, `as unknown as`, `as SomeType`, `<T>value`, `value!`,
  `@ts-ignore`, `@ts-expect-error`. Единственное исключение — `as const`.
- **Запрещён `any`**. Неизвестное значение приходит как `unknown` и разбирается схемой или type guard.
- **Всё входящее валидируется zod-схемой** из `shared` (тело/query/params ручки, ws-сообщение,
  строка из БД, содержимое `mock/*.json`, переменные окружения, `localStorage`). `JSON.parse` без
  последующего `.parse()` в код не принимается.
- **В тестах — те же правила**: фикстуры через типизированные фабрики или `safeParse`, не через касты.
- Отчёт обязан содержать сырой вывод `npx tsc --noEmit`, `npx eslint .` (0 ошибок) и
  `grep -rnE "\bas (any|unknown)\b|@ts-ignore|@ts-expect-error" src tests` (пусто).

## 5. Метрика экономии локального инференса

Ведётся с первой стадии: `metrics/local-savings.json` (+ методика в `metrics/README.md`).
Пересчёт — `npm run metrics`.

Откуда берутся числа: **из учёта токенов Hermes**, а не из оценок — `state.db` → `session_model_usage`
по сессиям воркеров (`billing_provider = 'custom'`, модель `kat-coder`) плюс `async_delegations`
для привязки сессий к батчам. Считаем: токены входа (`input_tokens` = cache miss,
`cache_read_tokens` = cache hit), токены выдачи (`output_tokens`), число обращений к модели,
настенное время батча против суммы времени воркеров (коэффициент параллельности и сэкономленные
секунды) и стоимость тех же токенов по прайсу DeepSeek V4.1 Flash и V4 Pro в обоих тарифах
(peak / off-peak). Экономия = стоимость по API − фактические локальные расходы (0).

Состояние на 2026-10-13 (2 батча, конец S1): 41 обращение к модели, вход 126 971 (miss) +
1 043 259 (hit), выдача 91 656 токенов; параллельность 1.475 (было бы на 460 с дольше
последовательно); те же токены на `deepseek-flash` — $0.077 (off-peak) / $0.154 (peak),
на `deepseek-v4-pro` — $0.288 / $0.576; локальные расходы $0. Финальные цифры — в JSON на стадии S12.

## 6. Коммиты и пуш (правило пользователя)

- Стадия (или пара «реализация + тесты») принята замером → **сразу коммит и push**. Не копить
  закрытые стадии в рабочем дереве.
- Пока батч воркеров в работе, файлы индексируются поимённо (`git add <пути>`), не `git add -A`:
  в коммит не должен попасть код, который в этот момент ещё правит воркер.
- Сообщения — на английском, Conventional Commits; один коммит = одна закрытая стадия или связанная пара.
- История коммитов повторяет роадмап: по `git log` видно, какие стадии закрыты и чем проверены.
- **Авторизация — SSH, без интерактивных окон.** Remote `origin` = `git@github.com:Verticool/transport-share.git`,
  ключ `~/.ssh/id_ed25519`. Git Credential Manager не используется; глобально выключены
  `credential.guiPrompt` и `credential.interactive`, поэтому ни push, ни fetch не поднимают окно
  с запросом доступа. Коммит — локальная операция, креды ей не нужны вообще: окно появлялось только
  на пуше по HTTPS.

## 7. Честность

- Если воркер сдал работу с дефектом, дефект остаётся в истории этого файла (что именно пришлось
  перепроверять), а не замалчивается.
- Любая строка «работает» в `STATUS.md` должна иметь ссылку на проверку в `docs/ACCEPTANCE.md`.

# DECISIONS.md — лог решений (ADR)

Формат: `ADR-NNN · решение` → контекст, выбор, альтернативы и почему отклонены, последствия.
Требование ТЗ: «промпты или лог решений сдаются вместе с кодом». Этот файл — тот самый лог.

---

## ADR-001 · Frontend: React 19 + Vite 8 + TypeScript

**Контекст.** ТЗ допускает Vue или React. Фронт плотно работает с картой, таймерами и WS.
**Решение.** React + Vite + TS, SPA.
**Альтернативы.** Vue 3 + Vite — равноценен технически, отклонён: экосистема shadcn/ui даёт
готовые примитивы, которые пользователь ожидает видеть (канонические компоненты, а не самопал).
**Последствия.** Vite 8 требует Node ≥ 20.19 — фиксируем Node 22 LTS.

## ADR-002 · Backend: Node.js 22 + TypeScript + Fastify 5

**Контекст.** ТЗ: Python/Go/Node, предпочтительно из списка.
**Решение.** Node + TS + Fastify. Причина №1 — общий `shared`-контракт (типы + zod-схемы) для фронта
и бэка: одна доменная модель вместо двух синхронизируемых вручную. Причина №2 — реалтайм (ws-хаб +
тик симулятора) в одном процессе без отдельного рантайма. Причина №3 — один базовый образ `node:22-alpine`.
**Альтернативы.** FastAPI (Python) — пришлось бы дублировать типы контракта и держать второй toolchain;
Go — лаконичнее по рантайму, но больше шаблонного кода для 15 ручек, выигрыша здесь нет.
**Последствия.** Отклонён NestJS: DI-контейнер и декораторы избыточны для 15 ручек (рулсет C1, C2).

## ADR-003 · Хранилище: PostgreSQL 17, доступ через `pg`, без ORM/Prisma

**Контекст.** ТЗ: реляционная СУБД, предпочтительно PostgreSQL. Проект локальный.
**Решение.** `postgres:17-alpine` + `pg` (Pool) + собственные SQL-миграции.
**Альтернативы.** Prisma — запрещён рулсетом (тяжёлая генерация, свой рантайм, миграции «в чёрном ящике»);
Kysely — типобезопасный SQL-builder, но вводит второй язык описания схемы. При гонках за самокат нужен
предикативный `UPDATE ... WHERE status='free'`, который на чистом SQL читается однозначно.
**Последствия.** Схема описывается вручную (миграции + CHECK/индексы), это компенсируется тестами на инварианты БД.

## ADR-004 · Реалтайм: WebSocket (`ws`) + снапшот/дельта с монотонным `seq`

**Контекст.** Требования B1 (состояние у всех сразу), B2 (мгновенный отказ второму), B7 (потеря связи).
**Решение.** Один ws-эндпоинт `/ws`: снапшот при подключении, дальше дельты парка; каждое сообщение
несёт `seq` и `sent_at`. `@fastify/websocket` + `ws`.
**Альтернативы.** SSE — только сервер→клиент, для «отказ приходит мгновенно» хватает HTTP-ответа,
но нет heartbeat-семантики и единого канала состояния; HTTP-поллинг 2 с — не выполняет «сразу»
и грузит сервер. Socket.IO — лишний протокол и вес.
**Последствия.** Нужна логика реконнекта и отбрасывания устаревших сообщений по `seq` (покрываем тестом).

## ADR-005 · Мок-данные: JSON-файлы в `mock/` + `MockApiClient`, не MSW

**Контекст.** Стадийность: сначала фронт целиком на моках, сервер позже. Решение пользователя (2026-10-13):
«псевдо-запросы к локальному json, засидить через локальную модель».
**Решение.** `mock/*.json` — общий источник: фронт фетчит те же файлы как статику Vite,
бэкенд на стадии S8 сидирует из них БД. Доступ через `ApiClient`-интерфейс с двумя реализациями.
**Альтернативы.** MSW — перехват на уровне сети выглядит реалистичнее, но добавляет service-worker
и усложняет отладку (не видно, что данные мок, в devtools не отличить от реальных); отдельный
mock-сервер — третий процесс и фронт без него не живёт.
**Последствия.** Контракт API фиксируется типами (S1) до появления сервера; риск расхождения
снимается тем, что zod-схемы — общие.

## ADR-006 · Состояние фронта: zustand (+ react-router 7), без TanStack Query

**Контекст.** Нужны: поток парка по ws, своя бронь/поездка, счета, история.
**Решение.** `zustand` для клиентского состояния и кэша серверных данных; запросы — через `ApiClient`
в экшенах стора. Роутинг — `react-router 7`.
**Альтернативы.** TanStack Query — мощный, но при живом ws-потоке большая часть инвалидации избыточна,
а проект локальный (рулсет C1: минимум зависимостей).
**Последствия.** Логика «загрузить/обновить» пишется руками — но она тонкая (список парка, активная
поездка) и покрывается тестами стора.

## ADR-007 · Карта: OpenLayers (`ol`) + подложка ArcGIS Light Gray Canvas

**Контекст.** Нужны маркеры парка, полигон зоны, попапы, зум/пан. Ключей платных провайдеров нет.
**Решение.** OpenLayers напрямую, без React-обёртки: контейнер через `useRef`, `Map`/`View`/`VectorLayer`
создаются в эффекте, данные слоя обновляются императивно через `VectorSource`. Подложка — XYZ
`World_Light_Gray_Base` с `server.arcgisonline.com` (порядок осей `{z}/{y}/{x}`), maxZoom 16,
атрибуция Esri обязательна. Библиотека выбрана пользователем (2026-10-13).
**Альтернативы.** Leaflet + react-leaflet — проще и компактнее, отклонён по решению пользователя;
`rlayers` (React-обёртка OL) — отклонена: лишняя зависимость, риск заброшенности, императивный API OL
всё равно протекает в код; MapLibre + векторные тайлы — лишний слой для растровых задач;
OSM-тайлы — по политике не предназначены для встраивания в сторонние приложения.
**Последствия.** Обновление маркеров идёт через `VectorSource`/`Feature`, а не через React-дерево,
поэтому поток парка не перерисовывает React-компоненты (плюс к производительности на 40+ объектах).
Провайдеры подложек — реестром в `config/`, смена провайдера = одна строка.

## ADR-008 · Деньги: целые минорные единицы (тыйын), поминутное округление вверх по интервалам

**Контекст.** Требование B4 («счёт по минутам… копейки не теряются»).
**Решение.** Хранение и расчёт — `bigint`/`number` в тыйынах; каждый интервал езды и каждая пауза
округляется вверх до полной минуты раздельно (`DOMAIN.md §5`).
**Альтернативы.** `numeric(12,2)` — корректно, но требует аккуратности с `pg` (строки) и не защищает
от `float` в TS; посекундная тарификация с точностью до тыйына — даёт «странные» копейки в счёте
и расходится с «по минутам» в ТЗ.
**Последствия.** Округление каждого интервала вверх осознанно консервативно для пользователя,
эталонные примеры зафиксированы тестами (`DOMAIN.md §5`).

## ADR-009 · Вход: email + пароль, JWT access (память) + refresh (httpOnly cookie)

**Контекст.** ТЗ A5 — модель входа на наше усмотрение.
**Решение.** bcryptjs (чистый JS — нет нативной сборки в alpine-образе), JWT 15 мин + refresh-cookie 7 дней.
**Альтернативы.** argon2 — лучше по стойкости, требует нативной сборки (`node-gyp`, python/make)
в контейнере; сессии в БД — плюс таблица и хранилище, для локального проекта избыточно.
**Последствия.** Гость видит карту без входа; бронь и поездка требуют авторизации.

## ADR-010 · Тесты: vitest везде, `app.inject()` вместо supertest, Playwright с `channel: msedge`

**Контекст.** Rулсет C8/C12, требование доказуемости (A13).
**Решение.** vitest в `shared`/`frontend`/`backend`, `@testing-library/react` для компонентов,
встроенный `app.inject()` Fastify для ручек (без сетевого порта и без supertest), Playwright для e2e —
с системным Edge, чтобы не тянуть Chromium (~700 МБ) в локальную машину.
**Альтернативы.** Jest — медленнее и требует отдельной настройки ESM/TS; Cypress — тяжёлый рантайм.
**Последствия.** e2e требует установленного Edge (есть на Windows 11 по умолчанию), это описано в RUNBOOK.

## ADR-011 · Docker: три контейнера, фронт-nginx проксирует `/api` и `/ws`

**Контекст.** ТЗ A1/A9/A11: отдельные клиент и сервер, общаются по сети, разворачивается локально.
**Решение.** compose с `frontend` (nginx:alpine, сборка Vite), `backend` (node:22-alpine), `db`
(postgres:17-alpine, том, healthcheck). Наружу — только фронт (8088) и БД (5434); бэкенд доступен
фронту по внутренней сети `app_net`; nginx проксирует `/api` и `/ws` (включая `Upgrade`).
**Альтернативы.** Отдельный контейнер-прокси (traefik) — третий лишний процесс; публиковать бэкенд
наружу и решать CORS — лишняя конфигурация и открытый порт.
**Последствия.** Порты 5434 и 8088 выбраны вне диапазона других локальных проектов на машине (5433 занят).

## ADR-012 · Симулятор транспорта: серверный тик 1 с, на фронт-стадии — тот же алгоритм в браузере

**Контекст.** Требование «транспорт с GPS и уровнем заряда — симулятор, входит в задание».
**Решение.** Алгоритм — чистый модуль в `shared/src/sim/` (шаг позиции, расход заряда, события).
На стадии S2–S7 его крутит фронт (`lib/simulator`, интервал 1 с), на S9 — бэкенд; код общий.
**Альтернативы.** Два независимых симулятора — гарантированное расхождение поведения моков и сервера.
**Последствия.** Симулятор обязан быть детерминированным при заданном seed — иначе тесты флакуют.

## ADR-013 · Часы: инъекция `Clock`, серверное время как источник истины

**Контекст.** Таймер брони 15 мин, поминутная тарификация, потеря связи, два клиента с разными часами.
**Решение.** `Clock` с `now()` прокидывается в сервисы и в UI; тесты используют ручные часы.
Каждый ответ API и ws-сообщение несёт `server_time`; фронт держит `useServerClock()` с drift-офсетом.
**Альтернативы.** `Date.now()` напрямую — тесты таймеров становятся медленными и флакующими.
**Последствия.** Запрет `Date.now()` в расчётах (рулсет C11), покрыт линт-правилом/ревью.

## ADR-014 · UI: русский язык, две темы с переключателем, shadcn/ui поверх Tailwind 4

**Контекст.** Продукт для пользователей в Бишкеке; пользователь проекта требователен к качеству UI.
**Решение.** Интерфейс полностью на русском (включая письма и тексты ошибок). Темы — светлая и тёмная
через CSS-переменные Tailwind 4 `@theme` в `global.css`, переключатель в хедере, по умолчанию светлая,
выбор хранится в `localStorage`. Компоненты — канонические shadcn/ui, цвета — только из токенов темы
(никаких `bg-green-100` в разметке), повторяющаяся разметка выносится в типизированные компоненты.
**Альтернативы.** Только светлая тема — отклонено: переключатель дешев и явно запрошен;
самописные компоненты — отклонено: пользователь ожидает канонические примитивы.
**Последствия.** Палитра статусов самоката (`free`/`reserved`/`in_ride`/`unavailable`) задаётся
конкретными значениями в `shared/src/constants.ts` и в токенах темы отдельно для светлой и тёмной схемы —
контраст на обеих темах проверяется визуально при приёмке.

## ADR-015 · Линтер: ESLint 10 (flat config) + Prettier в `npm run check`

**Контекст.** Проект пишется вместе с AI-воркером; нужен автоматический контроль стиля и типовых ошибок.
**Решение.** ESLint 10 с flat config в корне (общий для `shared`/`frontend`/`backend`), `typescript-eslint`,
`eslint-plugin-react-hooks` и `eslint-plugin-react-refresh` только для фронтенда, Prettier — единые правила
форматирования, `eslint-config-prettier` для расхождения правил. `npm run check` = `typecheck + lint + test`.
**Альтернативы.** Biome — быстрее, но экосистема плагинов React беднее; отказ от линтера — отклонено.
**Последствия.** Воркер обязан сдавать работу с чистым `npm run lint` (входит в критерии приёмки задач).

## ADR-016 · Git-flow: одна ветка `main`, коммиты после зелёных тестов, push в `Verticool/transport-share`

**Контекст.** Требование пользователя (2026-10-13): стадии коммитить по завершении тестов, репозиторий — GitHub.
**Решение.** Ветка `main`, remote `origin` = `git@github.com:Verticool/transport-share.git` (SSH).
Один коммит на стадию роадмапа (или на связанную пару «реализация + тесты»), сообщения на английском
в формате Conventional Commits, коммит делается только когда тесты стадии зелёные.
Авторизация — SSH-ключ (`~/.ssh/id_ed25519`, зарегистрирован в GitHub), Git Credential Manager в цикле
не участвует; глобально выставлены `credential.guiPrompt=false` и `credential.interactive=false`,
чтобы никакая git-операция не поднимала GUI-окно с запросом доступа.
**Альтернативы.** Ветка на фичу и PR — избыточно для одиночной разработки; коммиты «по ходу» — отклонено.
HTTPS + GCM (первый вариант настройки) отклонён после первого же пуша: GCM 2.7 показывает
интерактивное окно при каждой авторизации, что несовместимо с требованием «коммитить и пушить без
подтверждения пользователя».
**Последствия.** История репозитория = история роадмапа: каждый коммит соответствует закрытой стадии,
что упрощает сдачу (требование доказуемости).

## ADR-017 · Строгая типизация: запрет приведений типов, zod на всех границах

**Контекст.** Требование пользователя (2026-10-13): «хорошая валидация данных и строгая типизация»,
проект делается вместе с AI-воркером, а воркер любит закрывать несоответствие типов кастом.
**Решение.** Полный запрет `as`/`as unknown as`/`<T>`/`!`/`@ts-ignore` (исключение — `as const`),
запрет `any`, ESLint type-checked правила на error (см. `RULES.md §F`). Любые данные извне
(HTTP, WS, БД, `mock/*.json`, env, localStorage) входят как `unknown` и превращаются в доменный тип
только через zod-схему из `shared`. Внутри системы ходят провалидированные типы.
**Альтернативы.** `io-ts`/`valibot` — zod уже выбран как общий контракт фронта и бэка, второй валидатор
не нужен; ручные type guards вместо zod везде — больше кода и нет единой схемы для тестов и сида;
«мягкий» запрет кастов (warning) — воркер игнорирует предупреждения.
**Последствия.** Кода становится больше на границах (схема + `parse` на каждую ручку и ws-сообщение),
зато ошибка формы данных падает в одном месте и с понятным сообщением, а не через 3 экрана;
type-checked линт замедляет прогон, но это локальный проект.
Критерий приёмки стадии: `grep` на касты и `@ts-*` пуст, `tsc --noEmit` и `eslint` дают 0 ошибок.

## ADR-018 · Учёт экономии локального инференса: из учёта Hermes, а не оценками

**Контекст.** Пользователь хочет видеть, сколько работы сделали сабагенты на локальной модели
и сколько те же токены стоили бы на API DeepSeek V4.1 Flash (и V4 Pro). Оценка «на глаз» здесь
бесполезна: нужны реальные счётчики.
**Решение.** `scripts/collect-savings.mjs` читает `state.db` Hermes: `session_model_usage`
(по сессии воркера — `input_tokens` как cache miss, `cache_read_tokens` как cache hit,
`output_tokens`, `api_call_count`) и `async_delegations` (id батча, времена dispatch/completed,
цели задач для фильтра по проекту). Сессии привязываются к батчу по времени в их id
(`YYYYMMDD_HHMMSS_…` = `dispatched_at`). Результат — `metrics/local-savings.json`: токены,
параллельность (`sumTaskSeconds / wallClockSeconds`), сэкономленные секунды, стоимость по прайсу
DeepSeek в тарифах peak и off-peak, экономия = стоимость API − 0 (локальные маржинальные расходы).
**Альтернативы.** Парсинг логов `llama-server` (`print_timing` печатает prompt/eval-токены) —
работает, но привязка задач к воркерам идёт по времени и не даёт числа API-вызовов; ручной учёт
в чате — не доказуемо. Выбран учёт Hermes: он точнее и не зависит от раздутых логов.
**Последствия.** Цифры воспроизводимы одной командой (`npm run metrics`) на любой стадии, файл
коммитится и обновляется по ходу работы; методика и оговорки (электричество и износ GPU не учтены,
окна peak/off-peak у DeepSeek зависят от времени суток — показываем оба тарифа) описаны
в `metrics/README.md`.

## ADR-019 · Воркеру запрещено читать лишние файлы и работать вне целевой папки

**Контекст.** Первый опыт делегирования: воркер прочитал `docs/DOMAIN.md` и ещё несколько файлов,
из-за чего промпт вырос до ~58k токенов, модель держала слот 10 минут без прогресса препроцессинга
(зависание: `/slots` показывал `n_prompt_tokens_processed` без изменений), а другой воркер писал
файлы в подкаталог `cache/scratch` и копировал их в проект через `cp`.
**Решение.** В каждом задании воркеру явно указывается: (1) читать только перечисленный минимум
файлов, (2) писать строго в целевые пути, без `scratch` и `cp`, (3) при зависании оркестратор
останавливает воркера и проверяет, что он успел создать. Задания держатся на 1–2 файла.
**Альтернативы.** Увеличить контекст модели — не решает (проблема не в лимите, а в объёме
препроцессинга); разрешить `scratch` как «черновик» — теряется контроль над тем, что реально
попало в проект.
**Последствия.** Задания стали длиннее по формулировкам, зато зависаний больше не было; приёмка
всё равно идёт замером (`tsc`, `vitest`, grep), а не по отчёту воркера.
